# Монолит vs Микросервисы

## Монолитная архитектура
Что это: Всё приложение — единый код, единый процесс, единый деплой.
Пример: Django-приложение с одной БД.

## Микросервисная архитектура
Что это: Приложение разбито на маленькие независимые сервисы, каждый со своей БД.
Пример: Netflix, Amazon, Uber.

| Критерий               | Монолит                               | Микросервисы                              |
|------------------------|---------------------------------------|-------------------------------------------|
| Сложность разработки   | Низкая                                | Высокая                                   |
| Скорость деплоя        | Медленная (всё целиком)               | Быстрая (по частям)                       |
| Масштабирование        | Всё приложение                        | Только нужные сервисы                     |
| Отказоустойчивость     | Один баг → всё падает                 | Один сервис падает → остальные работают   |
| Командная работа       | Сложно (все в одном коде)             | Легко (команды изолированы)               |
| Технологический стек   | Один язык/фреймворк                   | Разные языки под задачи                   |
| Тестирование           | Проще (всё в одном месте)             | Сложнее (интеграция сервисов)             |
| Инфраструктура         | Простая                               | Сложная (оркестрация, сеть)               |
| Обратная связь         | Только после релиза                   | Быстрая (каждый сервис отдельно)          |

- Микросервисная архитектура — это эволюционный ответ на ограничения монолитных систем, особенно при росте сложности и масштаба приложений. Она предлагает модульность, независимость компонентов и гибкость в выборе технологий.
- Ключевые принципы микросервисов включают декомпозицию по бизнес-функциям, децентрализацию данных, независимое масштабирование и развёртывание, а также взаимодействие через чёткие API (REST, очереди сообщений).
- Каждая архитектура имеет свои сильные стороны: монолит проще на старте, он обеспечивает целостность данных и транзакций, а микросервисы дают гибкость, масштабируемость и устойчивость к отказам.
- Выбор архитектуры зависит от множества факторов, среди которых размер команды, требования к масштабируемости, необходимость технологической гибкости и уровень зрелости DevOps-процессов.

**✅ Когда что выбирать**
| Ситуация                                | Архитектура      |
|-----------------------------------------|------------------|
| MVP / Прототип                          | Монолит (быстро и просто) |
| Небольшая команда                       | Монолит          |
| Большая команда (20+ человек)           | Микросервисы     |
| Высокая нагрузка на разные части        | Микросервисы (масштабировать отдельно) |
| Разные технологии нужны                 | Микросервисы     |
| Частые релизы                           | Микросервисы     |
| Простота поддержки                      | Монолит          |

**Docker Compose** идеально подходит для микросервисов:
```yaml
services:
  auth:
    build: ./auth
    ports: "3001:3000"
  orders:
    build: ./orders
    ports: "3002:3000"
  payments:
    build: ./payments
    ports: "3003:3000"
```

Каждый сервис — отдельный контейнер, всё управляется через `docker-compose.yml`.

# Монолит vs Микросервисы

## Монолитная архитектура
Что это: Всё приложение — единый код, единый процесс, единый деплой.
Пример: Django-приложение с одной БД.

## Микросервисная архитектура
Что это: Приложение разбито на маленькие независимые сервисы, каждый со своей БД.
Пример: Netflix, Amazon, Uber.

| Критерий               | Монолит                               | Микросервисы                              |
|------------------------|---------------------------------------|-------------------------------------------|
| Сложность разработки   | Низкая                                | Высокая                                   |
| Скорость деплоя        | Медленная (всё целиком)               | Быстрая (по частям)                       |
| Масштабирование        | Всё приложение                        | Только нужные сервисы                     |
| Отказоустойчивость     | Один баг → всё падает                 | Один сервис падает → остальные работают   |
| Командная работа       | Сложно (все в одном коде)             | Легко (команды изолированы)               |
| Технологический стек   | Один язык/фреймворк                   | Разные языки под задачи                   |
| Тестирование           | Проще (всё в одном месте)             | Сложнее (интеграция сервисов)             |
| Инфраструктура         | Простая                               | Сложная (оркестрация, сеть)               |
| Обратная связь         | Только после релиза                   | Быстрая (каждый сервис отдельно)          |

- Микросервисная архитектура — это эволюционный ответ на ограничения монолитных систем, особенно при росте сложности и масштаба приложений. Она предлагает модульность, независимость компонентов и гибкость в выборе технологий.
- Ключевые принципы микросервисов включают декомпозицию по бизнес-функциям, децентрализацию данных, независимое масштабирование и развёртывание, а также взаимодействие через чёткие API (REST, очереди сообщений).
- Каждая архитектура имеет свои сильные стороны: монолит проще на старте, он обеспечивает целостность данных и транзакций, а микросервисы дают гибкость, масштабируемость и устойчивость к отказам.
- Выбор архитектуры зависит от множества факторов, среди которых размер команды, требования к масштабируемости, необходимость технологической гибкости и уровень зрелости DevOps-процессов.

**✅ Когда что выбирать**
| Ситуация                                | Архитектура      |
|-----------------------------------------|------------------|
| MVP / Прототип                          | Монолит (быстро и просто) |
| Небольшая команда                       | Монолит          |
| Большая команда (20+ человек)           | Микросервисы     |
| Высокая нагрузка на разные части        | Микросервисы (масштабировать отдельно) |
| Разные технологии нужны                 | Микросервисы     |
| Частые релизы                           | Микросервисы     |
| Простота поддержки                      | Монолит          |

**Docker Compose** идеально подходит для микросервисов:
```yaml
services:
  auth:
    build: ./auth
    ports: "3001:3000"
  orders:
    build: ./orders
    ports: "3002:3000"
  payments:
    build: ./payments
    ports: "3003:3000"
```

Каждый сервис — отдельный контейнер, всё управляется через `docker-compose.yml`.

Живой пример compose.yaml с двумя сервисами:

```yaml
# Имя проекта — все ресурсы будут иметь префикс "praktikum_"
name: praktikum

# Секция с сервисами (контейнерами)
services:
  # --- Сервис Prometheus (сбор метрик) ---
  prometheus:
    # Образ из Docker Hub
    image: prom/prometheus:v3.4.1
    # Имя контейнера (вместо автоматического praktikum_prometheus_1)
    container_name: prometheus
    # Аргументы командной строки при запуске
    command:
      - '--config.file=/etc/prometheus/prometheus.yml'  # Путь к конфигу внутри контейнера
    # Политика перезапуска: не перезапускать, если остановлен вручную
    restart: unless-stopped
    # Монтирование томов (сохранение данных между перезапусками)
    volumes:
      - prom_data:/prometheus  # Том prom_data → папка /prometheus внутри контейнера

  # --- Сервис Grafana (визуализация метрик) ---
  grafana:
    # Образ из Docker Hub
    image: grafana/grafana:12.0.2
    # Имя контейнера
    container_name: grafana
    # Проброс портов: хост:контейнер
    ports:
      - 3001:3000  # localhost:3001 → контейнер:3000
    # Политика перезапуска
    restart: unless-stopped
    # Переменные окружения внутри контейнера
    environment:
      - GF_SECURITY_ADMIN_USER=admin      # Логин для входа в Grafana
      - GF_SECURITY_ADMIN_PASSWORD=grafana # Пароль для входа в Grafana

# Секция с именованными томами (данные, которые живут вне контейнера)
volumes:
  prom_data:  # Будет создан том praktikum_prom_data
```

- Docker Compose — декларативный инструмент для управления многоконтейнерными приложениями через единый YAML-файл. Он упрощает разработку, тестирование и деплой.
- Основные сценарии применения: локальная разработка, изучение инструментов, создание тестовых сред в CI/CD и деплой простых приложений на одном хосте. Не подходит для распределённых высоконагруженных систем с автоматическим масштабированием.
- Ключевые элементы Compose-файла: services для описания сервисов (образы, команды, переменные окружения, тома, порты), networks и volumes для определения сетей и томов.
- Управление жизненным циклом осуществляется через команды docker compose up/down, start/stop, logs, exec, ps, что делает работу с многоконтейнерными приложениями интуитивно понятной.
- В Сompose по умолчанию создаётся изолированная bridge-сеть с автоматическим service discovery (сервисы доступны по имени). Можно создавать именованные сети для сложных топологий и изоляции.
- Переменные окружения задаются через environment или env_file.
- Именованные тома (volumes) обеспечивают сохранность данных и могут монтироваться в несколько сервисов.
- Compose соответсвует принципам 12-Factor App, в частности Config, Backing services, Dev/prod parity и Processes

| Директива   | Назначение                                                            | Ограничения                                                                                                     |
|-------------|-----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| `depends_on` | Управляет порядком запуска контейнеров                                | Не ждёт готовности сервиса (только запуска). Для проверки готовности — используйте `condition: service_healthy` |
| `extends`    | Управляет переиспользованием конфигурации                             | Не работает с `depends_on` и `volumes_from`. Не наследует `links` и `networks` из родителя                     |

# Масштабирование и балансировка

В микросервисных приложениях с растущей нагрузкой инженеры постоянно сталкиваются с одними и теми же вопросами: как пережить всплески трафика и не упереться в узкие места. Чтобы приложение оставалось стабильным, нужно разбираться в масштабировании сервисов и балансировке нагрузки.

**Масштабирование** — это процесс увеличения ресурсов системы для обработки большего объёма работы. Существует два основных типа масштабирования:
- **Горизонтальное:** добавление новых экземпляров приложения (например, количество серверов или контейнеров).
- **Вертикальное:** увеличение ресурсов одного сервера/контейнера (добавление CPU, RAM).

Когда речь заходит про современные микросервисные приложения, то лучше выбирать **горизонтальное**, и вот почему:

1. Отказоустойчивость. Если один сервер падает, остальные продолжают работать. При вертикальном масштабировании мы имеем одну точку отказа.

2. Гибкость. Количество инстансов можно менять динамически в зависимости от нагрузки — без остановки сервисов. При вертикальном масштабировании такой гибкости нет, и к тому же можно быстро упереться в физические пределы одного сервера.

3. Больше возможностей для обработки трафика. Запросы можно направлять на наименее загруженные инстансы или на ближайший регион. При работе с одним сервером таких возможностей нет.

Несмотря на все плюсы горизонтального масштабирования, не стоит демонизировать **вертикальное**. Иногда и оно бывает полезно:

- Монолитные приложения легче масштабировать вертикально, так как разделить их на несколько экземпляров зачастую невозможно.

- Базы данных иногда проще и эффективнее масштабировать вертикально, просто добавив ресурсов на сервер, а не настраивать сложную логику по репликации данных и балансировки нагрузки.

- При решении специфичных задач (например, при обучении ML-моделей).

## Масштабирование с Docker Compose

Чтобы изменить количество контейнеров сервиса, можно воспользоваться командой `docker compose scale web=3`
```bash
NAME                    IMAGE                            COMMAND                SERVICE   CREATED          STATUS         
scaling-example-web-1   katacoda/docker-http-server:v4   "python ./server.py"   web       6 minutes ago    Up 6 minutes    
scaling-example-web-2   katacoda/docker-http-server:v4   "python ./server.py"   web       15 seconds ago   Up 14 seconds   
scaling-example-web-3   katacoda/docker-http-server:v4   "python ./server.py"   web       15 seconds ago   Up 14 seconds   
```

Команда docker compose scale реализует императивный подход. Это значит, что после перезапуска окружения, количество контейнеров уменьшится до одного:
```bash
> docker compose up -d
✔ Container scaling-example-client-1  Running                                                                                                                  
✔ Container scaling-example-web-1     Running 
✔ Container scaling-example-web-3     Removed # Удалён, так как был создан в обход конфигурационного файла
✔ Container scaling-example-web-2     Removed # Удалён, так как был создан в обход конфигурационного файла
```
В редких случаях мы можем использовать команду `scale`, когда нужно быстро увеличить или уменьшить количество копий сервиса. Однако при управлении конфигурацией рекомендуется использовать декларативный подход, при котором желаемое состояние описывается в `compose`-файле и не отличается от запуска к запуску. 
Для масштабирования контейнеров с помощью декларативного подхода в `compose` используется поле `replicas` в секции `deploy`.

# Балансировка

Итак, вы настроили горизонтальное масштабирование, и теперь система сможет справиться с большей нагрузкой. Однако возникает новый вопрос: как распределить клиентские запросы по экземплярам приложения, да ещё так, чтобы их можно было обрабатывать максимально эффективно. Самое время поговорить о балансировке. 

**Балансировка** — это способ распределения нагрузки между несколькими сетевыми устройствами. Трафик распределяется равномерно или по какому-либо правилу, чтобы не перегружать сервера. Балансировщик можно реализовать программно или как отдельное сетевое устройство.

В задачи балансировщика входит:
- эффективное распределение клиентских запросов или сетевой нагрузки между несколькими серверами;
- обеспечение высокой доступности и надёжности — запросы отправляются только на те инстансы, которые готовы принимать трафик и обслуживать их;
- поддержка гибкого добавления или удаления серверов.

Балансировка трафика обычно происходит на двух уровнях: 

- **Четвёртый (транспортный) уровень (L4)**. Такой балансировщик называют NLB (Network Load Balancer). На четвёртом уровне он отслеживает сетевую информацию о портах и протоколах (TCP/UDP). В соответствии с алгоритмом балансировки он может доставлять трафик на сервер с наименьшим количеством подключений или сервер с наименьшим временем ответа.
- **Седьмой (прикладной) уровень (L7)**. Такой балансировщик называют ALB (Application Load Balancer). На седьмом уровне он уже осведомлён о работе приложения, так что можно выбирать более сложные алгоритмы балансировки. Например, с помощью протокола HTTP (на основе передаваемых куки-файлов) балансировщик может перенаправлять трафик от одного клиента на один и тот же сервер.

L4-балансировка быстрее, чем L7, так как работает на более низком уровне и не «анализирует» трафик. Если нужна более гибкая маршрутизация на уровне приложения — с учётом заголовков, URI и куки — а также дополнительные возможности вроде HTTP-healthcheck, SSL/TLS-терминации и rate limiting, то имеет смысл применять балансировку на прикладном уровне.

📊 Способы балансировки

| Метод               | Как работает                                   | Плюсы                                                      | Минусы                                                       |
|---------------------|------------------------------------------------|------------------------------------------------------------|--------------------------------------------------------------|
| Round Robin         | По очереди: 1→2→3→1→2...                       | Простой, легко реализовать                                 | Не учитывает нагрузку серверов                               |
| Weighted RR         | С учётом веса: мощный сервер получает больше запросов | Учитывает мощность серверов                         | Всё равно не смотрит на текущую нагрузку                    |
| Source IP Hash      | Хеш от IP клиента → всегда на один сервер      | Сессии сохраняются (корзина, авторизация)                  | Клиент привязан к серверу, проблемы при отказе              |
| Least Connection    | Запрос → сервер с наименьшим числом соединений | Учитывает текущую нагрузку                                 | Нужно отслеживать соединения                                 |
| Weighted LC         | Least Connection + вес сервера                 | Учитывает и нагрузку, и мощность                           | Сложнее в настройке                                          |
| Least Time          | Запрос → сервер с самым быстрым откликом       | Оптимально для производительности                          | Сложно реализовать                                           |
| Sticky Session      | Клиент привязан к серверу на время сессии      | Сохраняется состояние (корзина, логин)                    | Привязка к серверу, проблемы при отказе                     |

В качестве балансировщика мы будем использовать Nginx. Это известный и популярный инструмент, который может справляться с большой нагрузкой и поддерживает разные алгоритмы балансировки.

Пример реальной балансировки трафика:

```yaml
# Имя проекта — все ресурсы будут с префиксом "balancer-example_"
name: 'balancer-example'

# Секция с сервисами (контейнерами)
services:
  # --- Сервис Nginx (балансировщик) ---
  nginx:
    # Образ Nginx на Alpine (лёгкий)
    image: nginx:1.29-alpine
    # Проброс портов: 80 на хосте → 80 в контейнере
    ports:
      - 80:80
    # Монтируем конфиг Nginx из локальной папки
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
    # Запускаем только после katacoda-v2 и katacoda-v3
    depends_on:
      - katacoda-v2
      - katacoda-v3

  # --- Сервис katacoda-v2 (приложение v2) ---
  katacoda-v2:
    # Образ, который возвращает "v2" на запросы
    image: katacoda/docker-http-server:v2
    deploy:
      replicas: 2   # Запускаем 2 экземпляра (контейнера)

  # --- Сервис katacoda-v3 (приложение v3) ---
  katacoda-v3:
    image: katacoda/docker-http-server:v3
    deploy:
      replicas: 2   # Запускаем 2 экземпляра (контейнера)
```

```nginx
# Блок events — минимальная конфигурация для работы Nginx
events {}

# Основной блок http — настройки HTTP-сервера
http {
    # --- Бэкенд для v2 (с весами) ---
    upstream backend-v2 {
        # Сервер 1: вес 3 → получает 75% запросов
        server balancer-example-katacoda-v2-1 weight=3;
        # Сервер 2: вес 1 → получает 25% запросов
        server balancer-example-katacoda-v2-2 weight=1;
    }

    # DNS-резолвер Docker (127.0.0.11) для динамического обнаружения контейнеров
    resolver 127.0.0.11 valid=5s;

    # --- Бэкенд для v3 (DNS-резолвинг) ---
    upstream backend-v3 {
        # Зона для хранения состояния (64KB)
        zone katacoda-v3 64k;
        # Сервер с DNS-резолвингом — Nginx будет разрешать имя katacoda-v3 в IP контейнеров
        server katacoda-v3 resolve;
    }

    # --- Настройки HTTP-сервера ---
    server {
        # Слушаем порт 80
        listen 80;

        # === Маршрут /v2 ===
        location /v2 {
            # Проксируем запросы на бэкенд backend-v2 (с весами)
            proxy_pass http://backend-v2;
        }

        # === Маршрут /v3 ===
        location /v3 {
            # Проксируем запросы на бэкенд backend-v3 (DNS-резолвинг)
            proxy_pass http://backend-v3;
        }

        # === Маршрут /health (проверка здоровья) ===
        location /health {
            # Возвращаем ответ "OK" с кодом 200
            return 200 "OK";
            # Добавляем заголовок Content-Type: text/plain
            add_header Content-Type text/plain;
        }
    }
}
```

```merga
    Client[Клиент] -->|GET /v2| Nginx[Nginx]
    Client2[Клиент] -->|GET /v3| Nginx
    
    Nginx -->|Weighted RR 3:1| V2_1[katacoda-v2-1<br/>вес: 3 → 75%]
    Nginx -->|Weighted RR 3:1| V2_2[katacoda-v2-2<br/>вес: 1 → 25%]

```

|-------------------------------|---------------|--------------------------------|
| Weighted Round Robin (`/v2`)  | 75% / 25%     | ✅ Веса работают (3:1)         |
| Round Robin DNS (`/v3`)       | 50% / 50%     | ✅ Равномерное распределение   |

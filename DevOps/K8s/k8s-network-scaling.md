# Сетевое взаимодействие и доступ к приложениям

В Kubernetes сеть организована на нескольких уровнях. Каждый из них реализуется своим компонентом:

| Уровень сети      | Что это                              | Кто реализует                                |
|-------------------|--------------------------------------|----------------------------------------------|
| **Node Network**  | Сеть между нодами кластера           | Виртуальные и физические сетевые интерфейсы  |
| **Pod Network**   | Сеть между подами                    | CNI-плагин                                   |
| **Service Network** | Виртуальные IP для сервисов        | `kube-proxy`                                   |

**CNI-плагин** — ключевой компонент, который реализует Pod Network. Для этого он использует механизмы связности:

- внутри ноды: Bridge (Linux Bridge) — поды подключаются к виртуальному мосту;
- между нодами: Overlay (VXLAN) или Direct routing (BGP) — пакеты передаются через Node Network.

## Уровни сети в кластере

**Node Network** — это сеть, к которой подключены серверы кластера. В ней общаются Worker-ноды с Control Plane, ноды между собой и администратор с серверами.

![alt text](/pic/image.png)

**Pod Network** — виртуальная сеть для подов. При развёртывании кластера администратор задаёт диапазон адресов (CIDR); на каждую Worker-ноду выделяется подсеть, из которой подам назначаются IP-адреса.

![alt text](/pic/image-1.png)

Kubernetes предъявляет к Pod Network два ключевых требования (так называемая «плоская сетевая модель»):
1. Поды на разных нодах должны общаться между собой напрямую, без NAT.
2. Сервисы на ноде (например, `kubelet`) должны иметь прямой доступ к подам на этой ноде.

**Service Network** — виртуальная сеть для сервисов (подробнее — в следующем разделе). Сервисам назначаются виртуальные IP-адреса (ClusterIP), которые реализуются через правила балансировки на каждой ноде.

## CNI — реализация Pod Network

Реализацию требований к Pod Network обеспечивают CNI-плагины.

CNI (Container Network Interface) — это спецификация, которая описывает правила сетевого взаимодействия контейнеров и создания/удаления сетевых интерфейсов. Плагины CNI — отдельно устанавливаемые компоненты кластера, которые:
- создают сетевые интерфейсы для подов,
- назначают IP-адреса (через IPAM — IP Address Management),
- настраивают маршрутизацию между нодами,
- могут реализовывать NetworkPolicy.

![alt text](/pic/image-2.png)

| Элемент              | Значение                                                                 | Комментарий                                      |
|----------------------|--------------------------------------------------------------------------|--------------------------------------------------|
| **Pod CIDR кластера** | `10.1.0.0/16`                                                            | Общее адресное пространство для всех подов       |
| **Node Network**     | `192.168.1.0/24`                                                         | Обычная L2/L3-сеть между нодами                  |
| **Pod CIDR на ноду** | Worker 0 → `10.1.101.0/24`<br>Worker 1 → `10.1.102.0/24`<br>Worker N → `10.1.103.0/24` | Каждой ноде выдана своя подсеть из `/16`         |
| **Linux Bridge**     | `cni0` / `docker0`-подобный                                              | Соединяет veth-пары подов                        |
| **IP подов**         | `10.1.101.3`, `10.1.102.2`                                               | Из подсети своей ноды                            |

`ip route add 10.1.102.0/24 via 192.168.1.2` - Ключевой элемент. Это сердце всей схемы. Без неё Pod-to-Pod между нодами не заработает.
«Если пакет идёт на `10.1.102.x` (поды Worker 1) — отправляй его ноде `192.168.1.2` через её реальный IP.»
Соответственно, на Worker 1 должна быть симметричная запись:
`ip route add 10.1.101.0/24 via 192.168.1.1`

Популярные CNI-плагины: Calico, Cilium, Flannel (для простых сценариев), AWS VPC CNI, Azure CNI.

Сравнение Calico и Cilium:
- Calico — зрелое решение с поддержкой BGP-маршрутизации и мощными NetworkPolicy; хорошо подходит для корпоративных инсталляций.
- Cilium — использует eBPF для обработки трафика в ядре Linux; поддерживает L7-политики (HTTP, gRPC), встроенную observability.

## Механизмы связности Pod Network

Как CNI-плагин обеспечивает связность подов? Это зависит от их расположения — на одной ноде или на разных.

Внутри ноды используется Bridge (мост). Все поды на ноде подключаются к виртуальному мосту (Linux Bridge), который соединяет их с сетевым интерфейсом хоста. Это позволяет подам на одной ноде общаться напрямую через IP-адреса.

Между нодами CNI-плагин может использовать один из двух подходов:

| Подход                    | Как работает                                                                                                                                                    | Примеры                              |
|---------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------|
| **Overlay (VXLAN)**       | Пакеты Pod Network инкапсулируются в пакеты Node Network. Поды не видят физическую сеть — для них всё выглядит как единая L2-сеть.                              | Flannel, Weave, Calico (VXLAN mode)  |
| **Direct routing (BGP)**  | Ноды обмениваются маршрутами через протокол BGP. Пакеты идут напрямую без инкапсуляции — меньше накладных расходов, но требуется поддержка от сети.             | Calico (BGP mode)                    |

## Как приложения находят друг друга: Service и Service Discovery

Проблема, которую решает **Service Discovery**, звучит просто:
```text
Pod'ы эфемерны. Их IP меняются при каждом пересоздании. Как клиенту найти бэкенд, если адрес бэкенда живёт 5 минут?
```

**Service** — именованная абстракция доступа к набору подов. 
Набор подов задаётся селектором по меткам (`labels`). Kubernetes автоматически создаёт объекты `Endpoints` (и современный `EndpointSlice`), в которых хранятся актуальные IP и порты подов, подходящих под селектор. Service не хранит IP сам — он описывает, какие поды входят в сервис; трафик направляется по данным из `Endpoints`/`EndpointSlice`.

| Тип                            | Что даёт                                  | Доступ откуда              | Особенности                                                                                                                                                     | Когда использовать                                                                 |
|--------------------------------|-------------------------------------------|----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------|
| **ClusterIP**                  | Виртуальный IP внутри кластера            | Только изнутри кластера    | • По умолчанию<br>• IP не существует на интерфейсах<br>• Работает через kube-proxy (DNAT)                                                                       | Общение между сервисами внутри кластера (backend, db, cache)                       |
| **NodePort**                   | Порт на каждой ноде (`30000–32767`)       | Извне по `NodeIP:NodePort` | • Автоматически создаёт ClusterIP<br>• Порт открыт на всех нодах<br>• Ручной выбор порта или авто<br>• Не масштабируется красиво                              | Быстрый доступ для dev/test, on-prem без LB                                        |
| **LoadBalancer**               | Внешний облачный балансировщик            | Извне по внешнему IP       | • Автоматически создаёт NodePort + ClusterIP<br>• Работает только в облаке (AWS/GCP/Azure)<br>• 1 сервис = 1 LB = 💰<br>• В on-prem нужен MetalLB             | Прод-приложения, доступ из интернета                                               |
| **ExternalName**               | CNAME-запись на внешний домен             | Изнутри кластера           | • Не создаёт ClusterIP<br>• Не проксирует трафик<br>• Просто DNS-алиас<br>• Работает через CoreDNS                                                              | Обращение к внешним сервисам (RDS, внешний API) по внутреннему имени               |
| **Headless** (`clusterIP: None`) | DNS возвращает IP всех подов            | Изнутри кластера           | • Нет ClusterIP и балансировки<br>• kube-proxy не участвует<br>• Клиент сам выбирает под<br>• Каждому поду — своё DNS-имя                                       | StatefulSet (БД, Kafka, Zookeeper), когда нужен прямой доступ к конкретному поду   |

## NetworkPolicy, Ingress и Gateway API 

| Характеристика       | 🛡️ NetworkPolicy                              | 🚪 Ingress                                       | 🌐 Gateway API                                         |
|----------------------|-----------------------------------------------|--------------------------------------------------|--------------------------------------------------------|
| **Уровень OSI**      | L3/L4 (IP + порт)                             | L7 (HTTP/HTTPS)                                  | L4 + L7                                                |
| **Что это**          | Правила «кто с кем может общаться»            | Правила «какой HTTP-трафик куда направить»       | Новое поколение Ingress (более гибкое)                 |
| **Тип ресурса**      | Отдельный API-объект                          | Отдельный API-объект                             | Набор CRD (`GatewayClass`, `Gateway`, `HTTPRoute`)     |
| **Кто реализует**    | CNI-плагин (Calico, Cilium, Weave)            | Ingress Controller (nginx, traefik, HAProxy)     | Gateway Controller (Envoy, Istio, Cilium, nginx)       |
| **Зачем нужен**      | Изоляция трафика (firewall для подов)         | Публикация сервисов наружу по HTTP               | Замена Ingress: мультитенантность, L4+L7, роли         |
| **Уровень работы**   | Внутри кластера (Pod-to-Pod)                  | Вход извне в кластер                             | Вход извне + внутренний трафик                         |
| **Балансировка**     | ❌ Нет                                        | ✅ L7 (host/path)                                | ✅ L4 + L7                                             |

Ключевые выводы:

- CNI-плагин реализует Pod Network — назначает IP-адреса подам и обеспечивает их связность между нодами. Calico и Cilium — основные решения для продакшна.
- Service даёт стабильную точку доступа к набору подов по DNS-имени. Тип Service определяет область видимости: ClusterIP — внутри кластера, NodePort — по IP ноды, LoadBalancer — через внешний балансировщик.
- NetworkPolicy ограничивает трафик между подами. Работает по принципу «что не разрешено — запрещено» и реализуется CNI-плагином.
- Ingress обеспечивает HTTP/HTTPS-доступ извне с маршрутизацией по домену и пути. Для большинства задач Ingress достаточен.
- Gateway API — преемник Ingress с поддержкой gRPC и расширенной маршрутизацией. Актуален при подготовке к service mesh или когда нужны возможности, выходящие за рамки Ingress.

# Управление ресурсами и масштабирование в K8s

Для принятия решений о масштабировании важно понимать, сколько ресурсов потребляет приложение. Источник этих данных — метрики, которые собирают системы мониторинга (например, Prometheus и Grafana). Они позволяют анализировать историю потребления, тренды и паттерны нагрузки. 

Для быстрой диагностики Kubernetes предоставляет встроенный инструмент — команду `kubectl top`. 

```bash
kubectl top nodes

NAME                        CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
cl1-node-alot               250m         6%     1200Mi          30%
cl1-node-odow               180m         4%     980Mi           24%
cl1-node-ufyz               310m         7%     1500Mi          37% 
```

Здесь видно текущее потребление CPU (в миллиядрах) и памяти каждой ноды, а также процент от Allocatable-ресурсов.

У каждой ноды есть три ключевые величины:
1. `Capacity` — всё железо ноды;
2. `Reserved` — ресурсы, зарезервированные системой;
3. `Allocatable` — то, что можно раздать подам.

**Allocatable** = Capacity − System Reserved − Kube Reserved − Eviction Threshold 

Итоговое значение `Allocatable` — это объём ресурсов, на который ориентируется `scheduler` при выборе ноды для запуска пода. Поэтому в `kubectl` top процент рассчитывается именно от `Allocatable`, а не от `Capacity`.

## Как справляться с ростом нагрузки: масштабирование

Когда нагрузка на приложение растёт, нужно либо дать ему больше ресурсов (вертикальное масштабирование), либо запустить больше экземпляров (горизонтальное масштабирование). Kubernetes предоставляет инструменты для обоих подходов.

CPU — сжимаемый ресурс (compressible). Если под потребляет больше CPU, чем разрешено лимитом, Kubernetes применяет `throttling` — замедляет процесс, но не убивает его. 
По аналогии с краном, который можно прикрутить, — поток уменьшится, но не прекратится.

Память — несжимаемый ресурс (incompressible). Если под превышает лимит памяти, ядро Linux убивает процесс — `OOMKill` (Out of Memory Kill). 
Здесь вы будто пытаетесь поставить книгу на заполненную полку — если места нет, придётся убрать что-то старое.

- При нехватке CPU приложение начинает работать медленнее — в таких случаях обычно помогает горизонтальное масштабирование.
- При нехватке памяти процесс завершается с `OOMKill` — здесь требуется увеличить лимиты памяти (вертикальное масштабирование) или оптимизировать потребление ресурсов в коде.

|                        | ⬆️ Вертикальное                                              | ➡️ Горизонтальное                                      |
|------------------------|--------------------------------------------------------------|--------------------------------------------------------|
| **Что делаем**         | Увеличиваем ресурсы одного пода (CPU/RAM)                    | Увеличиваем количество подов                           |
| **Как в K8s**          | Меняем `resources.requests/limits`                           | Меняем `replicas`                                      |
| **Инструмент**         | Ручное + VPA (Vertical Pod Autoscaler)                       | HPA (Horizontal Pod Autoscaler)                        |
| **Простой**            | ⚠️ Требует пересоздания пода                                 | ✅ Без простоя (rolling update)                        |
| **Предел**             | Ограничен ресурсами одной ноды                               | Практически неограничен                                |
| **Стоимость**          | Дорого (мощные ноды)                                         | Дешевле (много обычных нод)                            |
| **Когда применять**    | БД, stateful, single-thread приложения                       | Stateless, API, web, воркеры                           |
| **Минусы**             | Downtime, потолок ноды                                       | Нужна stateless-архитектура                            |

## Vertical Pod Autoscaler (VPA)

VPA автоматически корректирует запросы на ресурсы (requests и limits) для подов на основе исторических данных о реальном потреблении. VPA состоит из трёх компонентов:

`Recommender` - Отслеживает метрики потребления ресурсов и формирует рекомендации
`Updater` - Проверяет текущее состояние подов и при необходимости пересоздаёт их
`Admission` Controller - Применяет рекомендованные значения при создании новых подов

```bash
kubectl describe vpa backend-vpa # посмотреть рекомендации VPA

Status:
  Recommendation:
    Container Recommendations:
      Container Name:  backend
      Lower Bound:
        Cpu:     25m
        Memory:  262144k
      Target:
        Cpu:     250m
        Memory:  524288k
      Upper Bound:
        Cpu:     1
        Memory:  1048576k 
```

Как работает:
- Смотрит на метрики (CPU, RAM, кастомные — RPS, очередь).
- Сравнивает с target (например, «держать CPU на 70%»).
- Меняет replicas автоматически.

## Horizontal Pod Autoscaler (HPA)

HPA автоматически регулирует количество реплик Deployment (или ReplicaSet, StatefulSet) на основе метрик потребления ресурсов. Это ключевой инструмент горизонтального масштабирования.

Как работает HPA:
1. Собирает метрики потребления ресурсов через Metrics API;
2. Сравнивает их с целевыми значениями;
3. Принимает решение об увеличении или уменьшении количества реплик;
4. Обновляет количество реплик в Deployment.

Для корректной работы HPA у подов в Deployment обязательно должны быть указаны `resources.requests`. HPA использует их для расчёта процента утилизации. Без `requests` HPA не сможет определить нагрузку. 

## Cluster Autoscaler

Что делать, если все ноды кластера заняты и новые поды не могут быть размещены (висят в Pending)? Механизм Cluster Autoscaler (CA) автоматически добавляет новые ноды в кластер, когда текущих не хватает, и удаляет ненужные, когда нагрузка падает.

- периодически проверяет, есть ли поды в состоянии Pending из-за нехватки ресурсов;
- если такие поды есть — увеличивает размер кластера (добавляет ноды);
- если какие-то ноды недозагружены и все поды можно перенести — уменьшает размер кластера.

**Cluster Autoscaler не управляет подами — он управляет нодами. Для масштабирования подов используйт**е HPA, а CA обеспечит, чтобы для этих подов были доступные ноды. 

## Планирование НОДов

| Механизм                     | Определение                                                              | Что решает                                              |
|------------------------------|--------------------------------------------------------------------------|---------------------------------------------------------|
| **NodeAffinity**             | Правило «под должен попасть на ноды с определёнными метками»             | Привязка пода к типу ноды (GPU, SSD, зона)              |
| **NodeAffinity (preferred)** | То же, но мягкое — «желательно, но не обязательно»                       | Приоритет нодам, но не блокировка                       |
| **PodAffinity**              | Правило «под должен попасть рядом с другими подами»                      | Разместить поды вместе (кэш, локальность)               |
| **PodAntiAffinity**          | Правило «под не должен попасть рядом с другими подами»                   | Разнести поды (HA, отказоустойчивость)                  |
| **topologySpreadConstraints**| Правило «распределить поды равномерно по топологии»                      | Баланс по зонам/нодам (zone-aware HA)                   |

**Ключевые выводы:**

- `kubectl top` позволяет быстро оценить потребление ресурсов подами и нодами. Для работы требуется Metrics Server.

- Deployment хранит историю ревизий в виде старых ReplicaSet. Команды `kubectl rollout` позволяют просматривать историю, проверять статус обновления и откатываться к предыдущим версиям.

- `RollingUpdate` обновляет поды постепенно без простоя; параметры `maxUnavailable` и `maxSurge` контролируют скорость и доступность. `Recreate` завершает все старые поды перед созданием новых — вызывает кратковременный простой.

- HPA автоматически масштабирует количество реплик на основе метрик CPU, памяти или пользовательских метрик. Для работы HPA у подов должны быть указаны `resources.requests`. VPA корректирует ресурсы подов; подходит для сбора рекомендаций и stateful-приложений.

- Cluster Autoscaler добавляет/удаляет ноды в кластере при нехватке/избытке ресурсов.

- Affinity и Anti-Affinity позволяют управлять размещением подов: притягивать к определённым нодам или другим подам (`nodeAffinity`, `podAffinity`), либо распределять по разным нодам и зонам (`podAntiAffinity`). `topologySpreadConstraints` обеспечивает количественный контроль равномерности распределения реплик через параметр maxSkew. Используйте мягкие правила (`preferred`) в production, чтобы не блокировать Deployment.

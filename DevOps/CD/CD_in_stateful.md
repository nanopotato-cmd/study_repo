# Особенности CD-процессов при работе со Stateful-приложениями

**Stateful-приложения** отличаются от stateless-приложений тем, что хранят состояние данных: после перезапуска они продолжают работу не с нуля, а с «сохранённой точки». Это заметно меняет подход к их развёртыванию и обновлению.

В то время как **stateless-приложения** можно легко масштабировать горизонтально, просто запуская новые экземпляры, stateful-приложения требуют особого подхода к управлению состоянием и данными.

Основные характеристики Stateful-приложений:

1. **Сохранение состояния** — приложение помнит информацию о предыдущих взаимодействиях.
2. **Зависимость от данных** — работоспособность зависит от сохранённых данных.
3. **Сложность масштабирования** — при добавлении нового экземпляра приложение должно быть написано так, чтобы общий источник данных или система кеширования не сталкивались с коллизиями при одновременной работе нескольких приложений.
4. **Критичность данных** — потеря данных может привести к полной неработоспособности.

## Что такое миграция баз данных

**Миграции баз данных** — это контролируемый процесс изменения структуры или схемы базы данных по мере развития проекта и приложения. Они позволяют фиксировать версии схемы, обновлять её по шагам и при необходимости откатываться к предыдущим состояниям.

Особенность здесь в том, что при каждом обновлении stateful-приложения может меняться схема данных. Чтобы деплой оставался безопасным и стабильным, нужно заранее продумать миграции, порядок их применения и возможность отката:

1. **Структурные изменения** — правки, которые меняют устройство таблиц: добавление новых, изменение существующих (добавление или удаление колонок), смена типов данных, а также добавление индексов и ограничений.
2. **Изменения данных** — правки содержимого: перенос данных, очистка устаревших данных, заполнение данными по умолчанию.
3. **Изменения связей** — правки, завязанные на ключи, индексы, триггеры и т. д.

Принципы безопасных миграций:

- **Идемпотентность** — миграция должна быть безопасной при повторном выполнении.
- **Атомарность** — миграция либо выполняется полностью, либо не выполняется вообще.
- **Обратимость** — возможность отката изменений.
- **Совместимость** — поддержка работы старой и новой версий приложения во время миграции.

## Работа с Flyway

Например, для накатывания миграций используют специальные инструменты — **Flyway** или **Liquibase**. Их общая идея проста: помимо основных таблиц приложения в базе создаётся дополнительная таблица, где хранится информация о том, какие версии миграций уже применялись. При запуске инструмент проверяет текущую версию схемы и выполняет только те миграции, которые ещё не выполнялись.

Основные команды:
- `migrate` — старт миграции. Запустятся все скрипты миграции, которые находятся в папке migration.
- `clean` — запустятся скрипты очистки базы (их надо самостоятельно прописать).
- `info` — показывает статус уже выполненных миграций и тех, которые можно применить, опираясь на данные из таблицы flyway_schema_history.
- `validate` — запустится встроенная проверка на корректность синтаксиса SQL-скриптов.

Миграционные скрипты подразделяются на типы:
- **Versioned migrations** — основные скрипты миграции, в которых создаются таблицы, схемы, пользователи, вносятся тестовые данные. Начинаются с `V001__`.
- **Undo migrations** — скрипты, предназначенные для отмены миграции. В них описывается, как будут удалены пользователи, таблицы базы и прочее. Начинаются с `U01__`.
- **Repeatable migrations** — скрипты, которые выполняются многократно: при каждом запуске приложения или изменении содержимого скрипта. Используются для выдачи прав пользователям, создания `VIEW`, функций и других задач. Запускаются последними, после всех скриптов миграции. Их имена начинаются с `R__`, потому что они повторяемые, их порядок не фиксируется, и номера версий для них не задаются.

Названия скриптов в миграции имеют очень важное значение, поэтому необходим строгий синтаксис и версионирование, указанные в названии файла `V01__` или `V1__`.

Как это будет выглядеть на примере:
```text
.
└── db
    └── migration
        ├── V001__dw.sql
        ├── V002__datasource.sql
        ├── V003__product_installation.sql
        └── R__access.sql
```
Классический пример миграционного скрипта, создающего схему и таблицу:
```sql
CREATE SCHEMA dw;
CREATE TABLE dw.user (
    id int PRIMARY KEY,
    name VARCHAR(100)
);
```

Адрес подключения к базе данных и расположение скриптов миграции указываются в конфигурационном файле `flyway.conf`. Вот пример конфигурации для SQL Server:
```text
# Указываем папки, в которых ведётся поиск миграцинных скриптов
flyway.locations=filesystem:db/migration,filesystem:db/bottom

# url для подключения к базе, включающий имя драйвера, хост, порт и имя базы
flyway.url=jdbc:sqlserver://192.168.1.30:1433;database=test

# Путь к драйверу, который используется для подключения к базе
# flyway.driver=

# Пользователь для подключения к базе
flyway.user=user

# Пароль для подключения к базе
flyway.password=sec_password

# Количество попыток подключения к базе
flyway.connectRetries=3

# Выбираем, до какой версии выполнять миграционные скрипты
flyway.target=4 
```

# Rollback и feature flag — механизмы безопасного внедрения изменений

## Rollback как механизм отката изменений

Deployment — это процесс развёртывания новой версии, а **rollback** — процесс возврата к предыдущей.

Повторно выполнить job деплоя, указав предыдущий тег версии. - Это и есть **rollback**: повторный деплой последней стабильной версии, обычно обозначенной предыдущим SemVer-тегом (например, 1.4.2). 
GitLab-CI, Kubernetes или любой другой инструмент просто разворачивает уже собранный артефакт — быстро, безопасно и без пересборки.

Однако **rollback** хорошо работает, только если проблема одна.
А теперь представьте, что в долгожданном релизе вместе с багом вышло ещё несколько важных фич. Что делать в такой ситуации? Откатывать всю версию целиком из-за одного сбоя — значит заморозить остальные улучшения, которые нужны пользователям.
Чтобы решить это, придумали подход **feature flag.**

## Feature flag как способ управления функциональностью

Фича-флаги (также известные как feature toggles или feature switches) — это техника, которая позволяет включать и выключать функциональность в приложении без передеплоя. Такой подход даёт гибкость при внедрении новых возможностей и помогает управлять рисками.
Представьте, что у вас есть новая функция, которая может быть нестабильной или требовать дополнительного тестирования. Вместо того чтобы полностью откатывать всю версию приложения, вы можете просто отключить эту конкретную функцию, а остальные не трогать.

Фича-флаги работают так:
- В коде приложения проверяется значение флага (обычно через переменную окружения или конфигурационный файл, иногда на уровне записи в отдельной табличке в базе данных).
- Если флаг включён — функция работает.
- Если флаг выключен — функция неактивна или работает в «безопасном» режиме.

```go
package main

import (
    "fmt"
    "os"
)

func main() {
    // Проверяем флаг через переменную окружения
    enableNewFeature := os.Getenv("ENABLE_NEW_FEATURE") == "true"

    if enableNewFeature {
        fmt.Println("Новая функция активна!")
        // Код новой функции
    } else {
        fmt.Println("Новая функция отключена")
        // Альтернативный код или заглушка
    }
} 
```
Существует несколько типов фича-флагов, каждый из которых решает определённые задачи:
- **Release flags** — используются, чтобы скрыть незавершённые функции от пользователей. Позволяют разработчикам интегрировать код в основную ветку, не показывая его пользователям.
- **Experiment flags** — позволяют проводить A/B-тестирование, показывая разным пользователям разные версии функции для оценки эффективности.
- **Operational flags** — используются для операционного контроля (например, отключение функции при высокой нагрузке на сервер).
- **Permission flags** — предоставляют доступ к функциям определённым группам пользователей (например, только администраторам или бета-тестерам).

Возможность легко откатываться и управлять отдельными частями приложения даёт вам большую гибкость. Когда в системе есть метрики и мониторинг ключевых функций, можно включать и выключать фичи для отдельных групп пользователей и смотреть на их поведение. Такая схема увеличивает свободу для экспериментов: сразу видно по графикам, какая фича «зашла», а какая нет. Дальше всё сводится к решению — включить её для всех или, наоборот, отключить флаг и вернуть всё как было.

## Rollback в GitLab-CI

В GitLab представлены несколько способов реализации отката:

1. **Ручной откат через интерфейс** — в разделе `Deployments` можно выбрать предыдущую версию и развернуть её заново.
2. **Автоматический откат при ошибке** — GitLab поддерживает автоматический откат через механизм `auto_stop_in` и правило `stop_environment`. Это позволяет вернуться к предыдущей версии, если новая не проходит health check или деплой завершается с ошибкой.
3. **Откат через API** — программное управление откатом через GitLab API.

## Фича-флаги в GitLab-CI

GitLab поддерживает фича-флаги на уровне пайплайнов через переменные и правила:

```yaml
variables:
  ENABLE_NEW_FEATURE: "false"

stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - echo "Building with feature flag: $ENABLE_NEW_FEATURE"
    - # Команды сборки с учётом флага

test:
  stage: test
  script:
    - echo "Testing with feature flag: $ENABLE_NEW_FEATURE"
    - # Команды тестирования
  rules:
    - if: $ENABLE_NEW_FEATURE == "true"
      when: always
    - if: $ENABLE_NEW_FEATURE == "false"
      when: manual

deploy:
  stage: deploy
  script:
    - echo "Deploying with feature flag: $ENABLE_NEW_FEATURE"
    - # Команды деплоя
  environment:
    name: production
    url: https://example.com
  when: manual
```

Дадим несколько практических рекомендаций по использованию rollback и фича-флагов.

Для rollback:

1. **Всегда сохраняйте артефакты** — убедитесь, что все версии приложения сохраняются в репозитории артефактов.
2. **Документируйте изменения** — ведите журнал изменений, чтобы понимать, что именно откатывается.
3. **Тестируйте откат** — регулярно проверяйте, что процесс отката работает корректно.
4. **Имейте план** — заранее определите, какие версии считаются стабильными и подходят для отката.

Для фича-флагов:

1. **Используйте осмысленные имена** — флаги должны иметь понятные названия, отражающие их назначение.
2. **Ограничивайте время жизни** — не оставляйте флаги навсегда, планируйте их удаление после стабилизации функции.
3. **Мониторьте использование** — отслеживайте, как часто включаются и выключаются флаги.
4. **Документируйте флаги** — ведите документацию по всем активным флагам и их назначению.
